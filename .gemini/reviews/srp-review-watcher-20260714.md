# SRP Review: app/watcher.py

**Date:** 2026-07-14
**Target File:** `app/watcher.py`
**Reviewer:** Clean Code Specialist

---

## 1. 責務の特定

`app/watcher.py` は、OCRバッチ処理の監視という目的のために、現在以下の責務を混在させています：

1.  **ファイル監視メカニズムの提供**: ポーリング実装 (`run_loop`) と `watchdog` ライブラリの利用ラッパー (`run_watchdog`)。
2.  **ファイル選定と安定性チェック**: ファイル拡張子フィルタリング (`is_image_file`)、書き込み完了チェック (`is_file_stable`)。
3.  **OCR処理プロセスのオーケストレーション**: `process_one` におけるOCR実行、座標正規化、構造解析のシーケンス制御。
4.  **ファイルシステム操作**: ディレクトリ作成、ファイルのリネーム/移動 (`shutil.copy2`)、一時ファイルのクリーンアップ (`unlink`)。
5.  **例外処理とリトライ制御**: 処理失敗時のリトライロジック、エラーディレクトリへの退避。
6.  **CLI環境構築**: 引数解析への依存 (`parse_args`) や `logging` 設定。

## 2. SRP 違反の特定

本モジュールは「神モジュール (God Module)」であり、**単一責任の原則 (SRP) を著しく違反**しています。

- **責務の過多**: ファイル監視のロジックと、具体的なOCRバッチ処理のビジネスロジックが同一ファイルに存在しています。
- **高結合**: `process_one` 関数が、OCRパイプライン、座標正規化、構造解析、ファイル操作を全てハードコードで制御しており、個々のコンポーネントが単体で動作・テストできません。
- **変更の連鎖**: 「監視間隔の変更」「OCRエンジンの切り替え」「ファイル退避ルールの変更」といった全く異なる理由の変更が全て本ファイルに影響を及ぼします。

## 3. 改善案の提示

この責務を分離するために、以下のクラス構造へのリファクタリングを推奨します。

### 推奨構造: サービス分離

責務ごとにクラスを分離します。

1.  **`FileMonitor` (監視層)**: 監視メカニズム (Polling/Watchdog) を抽象化し、新しいファイルが検出されたら「イベント」として通知する。
2.  **`ReceiptProcessor` (処理層)**: `process_one` のロジックをクラス化し、OCR・正規化・解析処理を委譲する。
3.  **`FileRepository` (永続化層)**: ファイルの移動、退避、クリーンアップを担当。

```python
# 構造案
class ReceiptProcessor:
    """ビジネスロジック: OCRから解析まで"""
    def __init__(self, pipeline, normalizer, parser): ...
    def run(self, image_path: Path): ...

class PollingMonitor:
    """監視メカニズム: 定期的にファイルを確認して処理を委譲"""
    def __init__(self, processor: ReceiptProcessor): ...
    def start(self): ...
```

### 具体的な改善方針

1.  **監視と処理の分離**: `watcher.py` から `process_one` 相当のロジックを削除し、監視用クラスと処理用クラスを別のファイルに分割します。
2.  **イベント駆動化**: `FileMonitor` は「新しいファイルが見つかった」というイベントを発行し、`ReceiptProcessor` がそれを購読する構造にします。これにより、ポーリングからウォッチドッグへの切り替えが処理ロジックに影響を与えなくなります。
3.  **ファイル管理の集約**: ファイル移動や安定性チェックは `FileRepository` 等の専用クラスに移動させ、`ReceiptProcessor` が直接 `shutil` を呼ばないようにします。
4.  **DI (依存注入) の利用**: OCRエンジンや解析エンジンの依存を `ReceiptProcessor` に注入することで、テスト時にモックに置き換えやすくします。

このリファクタリングにより、監視方式の変更や、OCRパイプラインの変更が互いに独立し、保守性が大幅に向上します。
