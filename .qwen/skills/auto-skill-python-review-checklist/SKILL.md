# Python 汎用レビューチェックリスト

## 目的

過去のPRレビューで蓄積された30の汎用的なPython品質項目を、コードレビュー時に自動探索・指摘する。このスキルは**プロジェクト固有の知識を一切使わず**、どのPythonアプリケーションにも通用する知見のみを扱う。

## 前提

- このスキルは **読み取り専用の探索** を行う。いかなるファイルも変更してはならない。
- レビュー対象のファイルパスまたはディレクトリが指定された場合、その範囲内を探索する。指定がない場合はプロジェクトルート全体を対象とする。
- 各項目は「発見された問題の数」と「該当箇所のコードスニペット」を報告する。

## 探索・指摘項目

### カテゴリA: リソース管理（接続・ファイルハンドル）

#### A-1: `sqlite3.Connection` のクローズ漏れ
- `with conn:` を使用しているが、`conn.close()` が `try...finally` で保証されていない箇所を探す
- **理由**: `with conn:` はトランザクションのコミット/ロールバックのみ管理し、`close()` は呼ばない。常時実行プロセスではコネクションリーク→`database is locked` に至る
- **探し方**: `get_db_connection` や `sqlite3.connect` の呼び出しを grep し、各呼び出し元で `close()` が `finally` ブロック内にあるか確認する

#### A-2: 読み取り専用操作でも接続クローズが行われているか
- SELECT クエリのみの関数でも、接続をクローズしているか確認する
- **理由**: 読み取り専用関数でもリークは発生する

#### A-3: `ThreadPoolExecutor` の使い回し
- 関数やループ内で毎回 `ThreadPoolExecutor()` を新規生成していないか
- **探し方**: `ThreadPoolExecutor` のインスタンス化を grep し、それがクラスインスタンス変数や `loop.run_in_executor` で使い回されているか確認する
- **改善**: `asyncio.get_running_loop().run_in_executor(None, sync_func, arg)` の使用を推奨

### カテゴリB: 辞書・Optional 安全アクセス

#### B-1: 辞書アクセスに `.get()` が使われているか
- `dict["key"]` 形式の直接アクセスを探す。特に戻り値が `None` になりうる関数の結果に対して
- **例外**: 直前に `if "key" in dict:` で存在確認している場合は許容

#### B-2: `None` 可能性のある戻り値のガード
- LLM クライアントやパーサーの戻り値が `None` の場合、呼び出し元でガード（`if result is None: return/continue`）が入っているか確認する
- **探し方**: `extracted = ...` や `result = ...` の直後に `if extracted is None:` などのガードがあるか

#### B-3: falsy 判定における `0` / `""` の巻き込み
- `x or y` 形式のフォールバックが、`0`（金額ゼロ）や `""`（空文字列）を正しく扱っているか
- **改善**: `x if x is not None else y` または `x if x not in (None, "") else y` の使用を推奨

### カテゴリC: 入力バリデーション・防御的プログラミング

#### C-1: リスト内要素の型チェック不足
- 座標やネストしたリストを処理する前に、`isinstance(p, (list, tuple))` や `len(p) >= n` のチェックが入っているか
- **探し方**: `for p in box:` や `min(...)` のジェネレータ式で、空シーケンスによる `ValueError` が発生しうる箇所

#### C-2: 関数入口での早期 return / None ガード
- 複数の分岐点で個別に None チェックするより、関数冒頭で `if not ocr_entries: return None` のように早期 return しているか

#### C-3: Optional 引数のフォールバック解決
- 複数のソースから値が得られる引数（例: `db_path`）が `None` で渡された場合、呼び出し側で `self.db_path or self.repository.db_path` のように解決してから渡しているか

### カテゴリD: パフォーマンス・冗長処理の排除

#### D-1: ループ不変の処理がループ内にないか
- ループの各イテレーションで同じ結果になる処理（例: `normalize_text(full_query)`）がループの内側にある場合、外に移動するよう指摘
- **探し方**: ループ内の `normalize_text`、`Path(...)`、`str(...)` 変換などがループ前に1回だけ実行可能か確認

#### D-2: 重複チェック・二重実行
- 上位のレイヤーで既にチェック済みの処理（例: `is_file_stable`）が下位でも再度実行されていないか
- **探し方**: 呼び出し階層を追跡し、同じチェック関数が直列に2回以上呼ばれていないか

#### D-3: 未使用の重い処理
- 結果を捨てるだけの I/O 処理（例: `_ = sorted(file_list)`）が存在しないか
- **探し方**: 戻り値が `_` に代入されている関数呼び出しのうち、重い処理（ファイル検索、DB クエリ等）を特定

#### D-4: デッドコード・重複ブロック
- 同じロジックが2箇所以上に存在する、または呼び出されていない関数が残っていないか
- **探し方**: コード内の重複パターン、および grep で未使用関数を特定

#### D-5: 不要な DB クエリの条件ガード
- 「値が変わっていないのに毎回 UPDATE が実行される」パターンがないか
- **探し方**: `UPDATE` 文の前に「現在値と新しい値の比較」が存在するか確認

### カテゴリE: 命名・一意性

#### E-1: 一意識別子に UUID を使っているか
- `f"{stem}-{field_name}"` のような手動生成の ID を使っていないか。同一エンティティの再処理時に `IntegrityError` の原因になる
- **改善**: `uuid.uuid4()` の使用を推奨

#### E-2: ファイル名マッチングのフォールバック
- 拡張子が異なるファイル（`.jpg` vs `.json`）を照合する場合、完全一致だけでなく `LIKE` 検索や `glob` による stem 一致のフォールバックがあるか

### カテゴリF: フレームワーク特有の落とし穴

#### F-1: `TemplateResponse` の引数渡し
- FastAPI の `TemplateResponse` がキーワード引数（`request=`, `name=`, `context=`）で正しく呼ばれているか。位置引数だと `request` と `name` が入れ替わり `unhashable type: 'dict'` になる
- **探し方**: `TemplateResponse(` の呼び出しを grep し、キーワード引数形式か確認

#### F-2: htmx ライブラリの読み込み
- htmx の属性（`hx-get`, `hx-put` 等）を使用する HTML テンプレートに `<script src="...htmx...">` が含まれているか

#### F-3: htmx レスポンスが生 JSON になっていないか
- htmx のエンドポイントが `{"status": "ok"}` のような生 JSON を返していないか。HTML フラグメントか `HX-Redirect` ヘッダーを返すべき

#### F-4: Jinja2 テンプレートパスが相対パスになっていないか
- `Jinja2Templates(directory="app/web/templates")` のような相対パス指定がないか
- **改善**: `Path(__file__).parent / "templates"` の使用を推奨

### カテゴリG: テキスト比較・正規化

#### G-1: テキスト比較前の正規化不足
- OCR テキストやユーザー入力の比較を行う箇所で、全角/半角統一、スペース除去、カンマ・通貨記号除去が行われているか
- **探し方**: `==` 比較や `in` 演算子、`difflib.SequenceMatcher` の使用箇所をすべて確認

#### G-2: 類似度比較に substring 判定を併用しているか
- `difflib.SequenceMatcher.ratio()` のみで判定している場合、余分な文字による類似度低下を考慮し、substring 判定も併用するよう指摘

### カテゴリH: エラーハンドリング・デバッグ

#### H-1: 使用モジュールの import 漏れ
- モジュール内で使用している関数/クラス（例: `unicodedata.normalize`, `uuid.uuid4`）が正しく import されているか
- **探し方**: ファイル先頭の import 文と、ファイル内で使用されているトップレベルシンボルを突合

#### H-2: `print()` デバッグ文の残存
- 本番コードに `print()` が残っていないか。特にモジュールレベルのスコープで実行されるもの
- **例外**: CLI ツールで `print()` が意図的な出力として使われている場合は許容

#### H-3: コメントと実装の乖離
- コメントが「`isinstance のみ`」と書いてあるのに実際には `dict` 判定がある、など実装と矛盾するコメントがないか
- **探し方**: コメント内の説明文と直後のコードを比較

### カテゴリI: アーキテクチャ・設計

#### I-1: デッドコードメソッドの放置
- リファクタリング後の新アーキテクチャで呼び出されていない旧メソッドが残っていないか
- **探し方**: 各公開関数・メソッドの呼び出し元を grep で追跡

#### I-2: 競合状態のハンドリング
- `get_or_create` パターンで、`INSERT` 時の `IntegrityError` を捕捉してフォールバック（`SELECT` 再試行）する設計になっているか
- **探し方**: `INSERT ... ON CONFLICT` や `try: INSERT / except IntegrityError: SELECT` のパターンを確認

#### I-3: テスト用引数の伝播
- `parse_args(argv)` のように引数を受け取る関数だが、内部で `sys.argv` を直接参照している箇所がないか。テストから引数を渡せない
- **探し方**: 引数で `argv` を受け取っている関数の内部で `sys.argv` が使われていないか

#### I-4: 正規化タイミングの不一致
- 同じデータが「正規化済みの値」と「未正規化の値」の両方で保存・比較されるパターンがないか（例: DB と JSON ファイルで値が異なる）
- **探し方**: データ保存/更新パスを追跡し、正規化関数が常に同じタイミングで適用されているか確認

#### I-5: スタイル設定の不一致
- フォーマッタ（black 等）の設定が `pyproject.toml` / `.vscode/settings.json` / `.editorconfig` 間で食い違っていないか
- **探し方**: 各設定ファイルの `line-length` や `target-version` を比較

## 重要度基準

| 重要度 | 基準 |
|--------|------|
| Critical | クラッシュ・データ損失・セキュリティ問題を引き起こす可能性がある |
| High | 機能障害・パフォーマンス低下・DB不整合の原因になる |
| Medium | 保守性・可読性・パフォーマンスに影響するが、即座の障害にはならない |
| Low | スタイル・命名・コメントの軽微な問題 |

## 注意点

- 各項目は、該当するコードが存在する場合のみ報告する。該当コードがない場合は「問題なし」と報告する。
- 同一の問題が複数ファイルで見つかった場合は、すべてのファイルパスを列挙する。
- 問題の指摘だけでなく、改善コードの例も提示する（推奨パターン）。
- プロジェクトの既存規約（QWEN.md 等）と矛盾する指摘はしない。例えば、そのプロジェクトで意図的に `x or y` パターンを使っている場合はスキップする。
- このスキルは **プロジェクトに依存しない汎用 Python 知見のみ** を扱う。プロジェクト固有のアーキテクチャ判断は対象外。
