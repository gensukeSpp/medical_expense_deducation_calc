# Issue #40 仕様: date 基準移行後の前方テンプレート補正の基底不一致修正

ブランチ `feature/date-relative-coords-normarize/39`（Issue #40 作業用）、実装で修正。
本ドキュメントはその振る舞い仕様。実装と整合する。（動作詳細の更新頻度の高い箇所は `.hermes/rules/coordinate-normalization.md` を参照。）

## 背景・目的

Issue #39 で `templates.coord_basis=='date'` に移行済みの clinic に対し、**移行後の別レシート**を
画像OCR / watcher 経路で処理するとき、前方テンプレート補正
（`ExtractionService._apply_template_corrections()`）が**topmost 基準の raw** に対して
**date 基準の `coords_corrections`** を照合してしまう不整合がある。

- `ImageProcessingService.process` / `ReceiptProcessor._sync_process` は
  `_normalize_coords`（topmost 化）→ `_parse_structured` → `apply_date_anchor_normalization`（date 化）の順。
- `_parse_structured` 内の前方補正は、その時点の raw（**topmost 基準**）に template 座標を照合する。
- `coord_basis=='date'` の template 座標は **date 基準**のため、基底不一致が起きる。
  - 一致しなければ補正が静かに機能停止し、偶発的な 50px 内マッチで別フィールドを誤上書きする恐れがある。

本仕様は、この基底不一致による**誤上書きを確実に防ぐ**ことを目的とする（誤上書き防止が主目的。機能回復は対象外）。

## 用語

| 語 | 定義 |
|----|------|
| 前方補正 | `_apply_template_corrections()` が template 座標を使って抽出値を補正すること |
| coord_basis | `templates` の座標基準識別列。値は `'topmost'`（従来）または `'date'`（#39 移行済み） |
| 座標駆動のフィールド上書き | `search_fields_by_proximity()` で template 座標近傍のテキストにより各フィールド値を引き直す処理 |

## 対応方針（確定: 案B・粒度1）

Issue #40 設計メモの **案B** を採択し、**粒度1** だけを実施する。

> **案B（粒度1）**: 移行済み clinic（`coord_basis=='date'`）では `_apply_template_corrections()` 内で
> `coords_corrections` を使う**座標駆動の処理を実行しない**。clinic 名の解決・正しい名への上書き・新規 clinic 作成は残す。

これにより誤上書きを**確実に**防ぐ最小変更となる。値はテキスト抽出（LLM）にフォールバックする。
移行済み clinic の前方補正の機能低下は許容する（受入条件として「無効化で誤上書きを防ぐ」を満たす）。

### なぜ案A でないか

案A（`_parse_structured` の前に date 化 → フル parse）は、date 解決に先立つ parse が必要という循環があり、
オーケストレーションを広く変更する。加えて「date 化を前へ動かす」ことは DB/出力へ波及し、回帰リスクが大きい。
案B（座標上書きを止める）は誤上書きを**確実に**防ぐ最小変更で、値はテキスト抽出にフォールバックするだけ。

## 修正対象: `_apply_template_corrections()` の 4 処理

`_apply_template_corrections()` 内の処理を 3 つに分け、`coord_basis=='date'` の扱いを定める。

| 処理 | 説明 | coord 使用 | date 基準での扱い |
|------|------|-----------|-----------------|
| ① clinic 特定（完全一致 / テキスト類似度） | `get_clinic_by_name` / `find_clinic_by_text_similarity` | 部分（レイアウト除く） | **残す** |
| ② 座標ベースのフィールド値上書き（`search_fields_by_proximity`） | 各フィールド値を template 座標から引き直す | **あり** | **スキップ**（これが誤上書きの原因） |
| ③ clinic 名の正しい名への上書き | `matched_clinic_name` | なし | **残す**（常に実行） |
| ④ 新規 clinic 作成 | `get_or_create_clinic` | なし | **残す** |

※ ①のうち「レイアウトマッチング（`match_template_by_layout`）」は `coords_corrections` を使うが、
  name 解決（完全一致/類似度）で template が見つからない場合のみ走る分岐のため、移行済み clinic では
  name 解決で template が得られれば入らない。実質的に回避される（完全排他は対象外として記録）。

## 判定条件

- `template.get("coord_basis") or "topmost"` で座標基準を取得。
- `coord_basis == 'date'` のときのみ、②（座標ベースのフィールド上書き）をスキップ。
- `coord_basis != 'date'`（`'topmost'` または旧データ NULL→`or "topmost"`）なら従来どおり座標上書きを実行。

```python
# app/structural_parser.py _apply_template_corrections() 内、テンプレート適用ブロック
if template and matched_clinic_name:
    coord_basis = template.get("coord_basis") or "topmost"
    if coord_basis != "date":  # 移行済み(date)は topmost raw に照合不可 → 座標上書きをスキップ
        coords = template.get("coords_corrections")
        if coords:
            ocr_entries = self._get_ocr_entries(ocr_json)
            if ocr_entries:
                proximity_texts = search_fields_by_proximity(
                    ocr_entries, coords, threshold=DEFAULT_PROXIMITY_THRESHOLD
                )
                for field_name, concat_text in proximity_texts.items():
                    if concat_text and field_name in extracted:
                        extracted[field_name] = concat_text
    # 正しいクリニック名で上書き（③）は coord_basis に関係なく常に実行
    if matched_clinic_name != clinic_name:
        extracted["clinic"] = matched_clinic_name
```

1. 移行済み clinic（`coord_basis=='date'`）のレシートで、前方補正による座標上書きが実行されない。
2. 誤上書きが起きない（レシート左上の見出し/クリニック名が金額・日付に混入しない）。

## 補足（coord_basis=None について）

`templates.coord_basis` は `TEXT NOT NULL DEFAULT 'topmost'` のため、**スキーマ上 NULL は入らない**。
旧データも 'topmost' として読まれる。`or "topmost"` は純粋な防御用（None が来た場合の安全側フォールバック）。
そのため「coord_basis=None（旧データ）」の専用テストは設けず、既存の `test_template_based_extraction_override`
（デフォルト topmost）が実質カバーする。
