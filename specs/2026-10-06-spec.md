# Issue #39 仕様: 日付基準による OCR box 座標正規化

ブランチ `feature/date-relative-coords-normarize/39`、コミット `d0dd617` で実装。
本ドキュメントはその振る舞い仕様。実装と整合する。（動作詳細の更新頻度の高い箇所は `.hermes/rules/coordinate-normalization.md` を参照。）

## 背景・目的

現状は OCR 結果の全 box から最小 x/y を求め、その基準（topmost/leftmost）で座標を正規化している。
一方、構造化出力の `date` は領収書内の複数の日付候補から抽出されるため、抽出元の OCR box が分からず、
「日付を基準にした正規化」へ直接は切り替えられない。

本仕様は、フォーム修正で `templates.coords_corrections["date"]` が学習された後の**同 clinic/layout** において、
その座標を手がかりに日付候補を選択し、**信頼できる場合に限り date box の左上を基準として全 OCR box を再正規化**する。
初回・date 座標未学習・候補が曖昧な場合は従来の topmost/leftmost 基準を維持する。

## 用語

| 語 | 定義 |
|----|------|
| topmost/leftmost 基準 | 全 box の最小 x/y を原点とする従来の正規化（`coord_normalizer.normalize_coordinates`）|
| date 基準 | 選択した date box の左上 (min_x, min_y) を原点とする正規化 |
| coord_basis | `templates` の座標基準識別列。値は `'topmost'`（従来）または `'date'` |

## 全体フロー（画像OCR / watcher 経路）

```
1回目OCR -> raw_data.json (絶対座標)
  -> normalize_coordinates() (topmost/leftmost 正規化、既存)
  -> 構造化 parse (date / clinic 抽出)     … 低Confidenceなら preprocessing retry (既存)
  -> apply_date_anchor_normalization():
       1. clinic の最新 template から template date coords を取得
           … date coords 未学習なら何もしない (従来方式)
       2. resolve_date_anchor() で信頼できる date box を解決
       3. normalize_coordinates_by_anchor(raw, date box) で raw を date 基準へ再正規化
       4. template が topmost なら update_template_basis() で date 基準へ移行 (履歴保存・二重変換防止)
       5. update_receipt_ocr_json_by_source() で DB の receipts.ocr_json を新基準へ更新
```

## 入力 / 出力

| 対象 | 入力 | 出力・事後状態 |
|------|------|----------------|
| raw_data.json | topmost 正規化済み OCR エントリ列（`{text, confidence, box}`）| 信頼時は date 基準へ上書き（date box 左上が (0,0)）。不可時は未変更 |
| templates | `coords_corrections`（topmost 基準）| 信頼時・初回のみ date 基準へ移行、`coord_basis='date'`。旧座標を履歴保存 |
| receipts.ocr_json | DB 保存済み box | 信頼時に date 基準で更新（二重登録なし）|
| structured_data.json | — | 変更なし（値はテキスト抽出に由来し座標基準に非依存）|

## date anchor の解決条件（`resolve_date_anchor`）

1. `structured_date` を `parse_date()` で正規化。`None` なら解決しない。
2. OCR エントリのうち `parse_date(text) == structured_date` の候補を列挙。
   - 候補 0 件 → 解決しない（従来方式）。
3. **template date coords が未学習（存在しない）→ 解決しない**（受入条件1）。
4. 候補が 1 件 → それを採用（template basis が date でも可）。
5. 候補が複数:
   - template が `topmost` 基準のときのみ、`search_by_proximity()` の中心距離で
     `proximity_threshold`（デフォルト 50px）以内に**一意に**近い box を採用。
   - 距離が曖昧・競合、または template が `date` 基準の場合は解決しない（従来方式）。

## 使用する閾値（既存値を維持・新規閾値は導入しない）

| 項目 | 値 | 出典 |
|------|----|------|
| proximity（候補絞り込み）| 50.0 px | `DEFAULT_PROXIMITY_THRESHOLD` / `resolve_date_anchor` |
| テキスト照合 | `parse_date()` ISO 一致 | 表記ゆれ（`2026/01/15` と `2026年1月15日`）を同一比較 |
| 低 Confidence ゲート | 0.8（既存）| anchor は低Confidence判定**後**に実行 |

## DB スキーマ変更

`templates.coord_basis TEXT NOT NULL DEFAULT 'topmost'` を追加。
既存 DB は `db_migrations` の idempotent 移行（`PRAGMA table_info` で存在確認 → `ALTER TABLE ADD COLUMN`）で対応。

## 設計判断と根拠

| 判断 | 決定 | 根拠 |
|------|------|------|
| 再解析はしない | 再正規化後に `process_input_json` を再実行しない | `process_input_json` は呼び出しごとに新しい receipt 行を insert するため、再解析すると**同一画像のレシートが二重登録**される。構造化値は座標基準に非依存なので不要 |
| DB 同期法 | `update_receipt_ocr_json_by_source()` で ocr_json を date 基準へ更新（二重登録なし）| 受入条件6。最も一致する row のみ更新 |
| 基準切替は一度だけ | `update_template_basis()` は `coord_basis=='date'` なら no-op | 受入条件4（二重変換防止）|
| 履歴保存 | 同一トランザクションで移行前 coords を `template_history`（`change_reason='basis_migration'`）に保存 | 受入条件4（部分更新防止）|
| path 統合 | 画像OCR / watcher 経路のみ。`process_input_json` は無変更 | 後方互換。`--input-json` 単体は従来動作 |
| 後方互換 | `normalize_coordinates()` は無変更 | 従来正規化の保存 |

## 受入条件と対応

1. date 未学習 clinic → 従来正規化維持（`resolve_date_anchor` が None）
2. 学習後の同 clinic/layout で候補が信頼できれば date box 基準で正規化
3. 重複日付・照合失敗・曖昧距離 → 誤候補を避け従来方式へフォールバック
4. 基準切替は一度だけ、旧座標は履歴に残り、修正時の近傍検索が新基準で継続
5. low-confidence gate と preprocessing retry は既存挙動を維持
6. raw / DB ocr_json / template feedback が date 基準で一致
7. 既存テスト + 追加回帰テストが成功

## 既知の課題（次 Issue #40）

実装後の調査で、date 基準移行後に残るオーケストレーション順序由来の不整合を確認。次 Issue として起票済み。

- **Issue #40**: `[Bug] date 基準移行後の前方テンプレート補正で座標基準が不一致`
- 参照: https://github.com/gensukeSpp/medical_expense_deducation_calc/issues/40

### 内容

- `ImageProcessingService.process` / `ReceiptProcessor._sync_process` は
  `_normalize_coords`（topmost 化）→ `_parse_structured` → `apply_date_anchor_normalization`（date 化）の順。
- `_parse_structured` 内の `ExtractionService._apply_template_corrections()` は、その時点の raw（**topmost 基準**）に対し
  `search_fields_by_proximity(ocr_entries, coords)` で template の `coords_corrections` を照合する。
- しかし `coord_basis='date'` に移行済みの clinic では template 座標は **date 基準**。
  → template(date) × raw(topmost) で基底不一致。一致しなければ補正が静かに機能停止し、
  偶発的な 50px 内マッチで別フィールドを誤上書きする恐れ。

### スコープと現状の確認

- 画像OCR / watcher 経路のみが対象（`process_image` / `process_input_json` は既存経路のため対象外）。
- 逆方向（フィードバック学習 `_resolve_coord_results`）は raw・template が共に date 基準で一致するため問題なし。
  ref. `app/services/ocr_coordinate_service.py:127-152`
- 追加テストは「初回移行」を検証しており、「移行済み clinic の次レシートでの前方抽出」は未検証（→ Issue #40 で回帰テスト追加）。

### 対応方針（Issue #40 本文の設計メモ）

- **案A**: `_parse_structured` の前に raw を date 基準へ再正規化（順序入れ替え）。軽量テキスト抽出で anchor 解決 → date 化 → フル parse を1回。二重登録とは無関係（軽量抽出は persist しない）。重複日付＋移行済みでは近接参照不可のため topmost のまま。
- **案B**: 移行済み clinic（`coord_basis=='date'`）の `_apply_template_corrections` をスキップし誤上書きだけ防ぐ（機能低下は残る）。
- **案C**: 起票のみ（本 Issue）。実装は方針確定後に別途実施。

※ 本仕様（#39）の実装では案Cとして Issue #40 を起票したのみで、実装は未着手。
